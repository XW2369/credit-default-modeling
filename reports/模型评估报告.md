## §3 统计检验结论（护城河）

### 3.1 AUC 必须带置信区间

AUC 是基于样本估计的**点**，存在抽样误差。本次结果：

- LR：AUC **0.7587**，95% CI **[0.7458, 0.7709]**
- XGB：AUC **0.7540**，95% CI **[0.7414, 0.7668]**

两个数只差 0.005，区间**大面积重叠**。

> ⚠️ **关键**：两个 95% 置信区间重叠，**不能**推出"差异不显著"。区间各自覆盖真值是边际命题，而"两者之差是否为 0"要看**差值的分布**。正确做法：成对 Bootstrap 重采样构造 **AUC 差值**的置信区间，或使用 **DeLong / Hanley-McNeil 检验**。
> 本次未做差值检验，因此严谨表述是：**"排序能力接近"**，而非"无显著差异"。

### 3.2 McNemar 检验（固定阈值层面）

- AUC 衡量**全阈值下**的排序能力；McNemar 检验的是**单一固定阈值下的分类对错**。
- 不使用配对 t 检验的原因：K 折 CV 各折训练样本重叠、AUC 彼此不独立，t 检验据此估计的方差被低估、自由度虚高，p 偏小、假阳性率上升。
- 本次结果：**b = 474**（A 对 B 错）、**c = 844**（A 错 B 对）、**p = 1.4 × 10⁻²⁴**（精确二项检验）

结论：**在 0.5 阈值下，XGBoost 比逻辑回归少错 370 个样本，差异极显著。**

> ⚠️ **操作点限定**：本实验中 LR 用了 `class_weight="balanced"`，其 0.5 阈值的含义与 XGBoost 不同，两者不在同一操作点上。于是出现看似矛盾、实则各答一题的结果：**排序层面（AUC，不依赖阈值）两者区间重叠、排序能力接近；阈值层面（McNemar）XGBoost 显著少错。**

### 3.3 上线前需要多少样本

- 基线违约率 `p1 = 0.2212`，**假定待检测效应量**为相对提升 10% → `p2 = 0.2433`
- α = 0.05、power = 0.8 → **每组 5,719 条，两组共约 11,438 条**
- 手上全量测试集 **9,000 < 11,438**

> 注：10% 是**假定要检测的效应量**，不是观测到的增益。
> 结论：**即便动用全部测试样本，也不足以在 α=0.05、power=0.8 下证明 10% 的相对提升不是噪声。**任何"某模型提升了 X%"的表述都必须附置信区间或检验结论，否则只是噪声的另一种说法。

## §4 SHAP 解读

SHAP 值量化每个特征对模型预测分数的**边际贡献**：正负号代表方向，绝对值代表大小。

**本次结果（`reports/figures/shap_summary.png`）**：

1. **`pay_0_woe` 排第一**——与 Day2 的 IV 表（IV = 0.8736 居首）**完全吻合**。两套完全独立的方法（IV 基于分箱统计，SHAP 基于树模型的博弈论分解）给出同一个答案，这叫交叉验证。
2. 后续为 `pay_2_woe`、`limit_bal_woe`、`pay_3_woe`——近两期还款状态 + 授信额度，符合信贷业务直觉。
3. **方向解读**：图上第一行，**蓝色点（WOE 值低）全部落在右侧（SHAP 为正，最高 +1.8），红色点（WOE 高）落在左侧**。
   链条是：WOE 定义为 `ln(P(好客户)/P(坏客户))` → **WOE 低 = 该箱内还款状态差的客户居多** → 模型输出 P(违约=1) 被推高。方向与业务直觉一致。

> SHAP 依赖模型内部打分函数，特征重要性是"**预测贡献**"，**不等同于因果效应**。高 SHAP 特征不代表该特征会直接造成客户逾期，只能说明模型用它做了判断。

## §5 上线建议：排序场景 vs 阈值场景

区分两类业务场景，不能一刀切：

1. **纯排序场景**（客户风险分层、营销优先级、额度分档）：依赖整条 ROC 曲线的全局排序能力，看 AUC。当前两模型 AUC 点估计接近、区间重叠，**未做差值检验前不建议以"AUC 更高"为由替换上线**。
2. **固定阈值审批场景**（授信准入、自动拒件）：依赖单一 cutoff 做通过/拒绝决策，此时 McNemar 更有参考价值。即便全局排序差异不显著，只要**业务切点附近的分类结果差异显著**（本次 p = 1.4×10⁻²⁴），就必须仔细评估：新模型拒绝的是哪批客群、误拒与误放各自的业务代价，权衡资产损失与误拒成本后再定。

**小结**：`xgb_tuned` 在 AUC 点估计上最高（0.7756），但上线决策不能只看点估计。排序场景需先补 AUC 差值检验；阈值准入场景除统计显著性外，还必须评估业务损益与错分成本。**另需注意：xgb 未调参时 Brier = 0.1431 为四者最低，校准最好——若业务要的是"概率准"而非"排序准"，这一点比 AUC 更重要。**

## §7 已知问题复盘：WOE 错位 bug（本次最重要的发现）

### 怎么发现的：baseline 体检

模型基线训练完成后做效果体检，发现 **AUC ≈ 0.50、PR-AUC ≈ 0.22（等于正样本率）、单特征相关系数 ≈ 0.004、KS ≈ 0.02**——等同于随机猜测。这是强烈异常信号，触发深度排查。值得注意的是：**单元测试全部通过，代码没有任何报错**，因此初期极难定位。

### 怎么定位的：30% / 70% 的概率账

先做**单特征体检**：`pay_0_woe` 的 IV 高达 0.87，但它单独对 y 的 AUC 只有 0.5039、相关系数 0.006——**特征与标签彻底解耦**，说明问题不在模型，在数据对齐。

再看数据：train 有 **6,242 / 21,000（29.7%）** 行、test 有 **6,303 / 9,000（70%）** 行**全部 13 列同时为 NaN**。这个不对称本身就是线索。

账是这么算的：

- 根因在 `_assign_bins` 返回 `index=range(len(x))` 的 Series（**丢弃了原始索引**），而 `woe_transform` 用 `index=df.index` 接收 → pandas **按索引对齐**，两套索引对不上。
- train 是从 30,000 行里切出的 21,000 行，索引散布在 0–29,999；而对齐表只有 0–20,999 的位置。于是**原始索引 ≥ 21,000 的行全部匹配不到 → 变 NaN**，概率 = 9,000/30,000 = **30%**（实测 29.7%）。
- test 同理：索引 ≥ 9,000 的概率 = 21,000/30,000 = **70%**（实测 70%）。
- 而**正样本率是 22.12% / 77.88%**——与 30%/70% 完全无关，两者不可混淆。

第二刀：`eda.py` 里 `train_m["y"] = y_tr.to_numpy()` 是**按位置**赋值的，y 列的顺序是对的，而 WOE 列是索引乱序的 → 特征和标签彻底错配 → 模型只能学到边际概率 → AUC 跌到 0.50。

### 怎么修的：按位置对齐

`woe_transform` 改为：**numpy 按位置分箱（`np.digitize`），列表按位置写回**，全程不碰索引。

```python
bins = np.digitize(np.asarray(df[feat], dtype=float), edges)
out[f"{feat}_woe"] = [woe_map[int(b)] for b in bins]
```

修复后：数据**零丢行**（21,000 / 9,000 全部有效），baseline AUC 从 0.50 恢复到 0.7587。

> 影响范围澄清：`fit_woe` 与 IV 表是按位置算的，**IV 表、手推公式、EDA 四张图全部无罪**；坏的只有 `woe_transform` 的输出，即喂给建模的那张表。

### 教训（三条）

1. **单元测试全绿 ≠ 端到端正确**。测试只验证了 WOE 公式本身，没校验"整条流水线里特征向量和标签的行序全程对齐"。
2. **这类 bug 不会抛异常、不会崩溃，只会静默产出完全无效的模型**——隐蔽性极强，是风控建模的高危 bug。对策：流水线每一步后加**位置一致性校验**（行数、索引、顺序）。
3. **baseline 体检必须做**：AUC ≈ 0.50 这种"看起来能跑"的数字，是唯一能在早期暴露上游错误的信号。**模型跑通不等于数据正确。**
